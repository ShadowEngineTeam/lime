Left out, as nothing in bgfx-files.xml builds or includes them: examples, bindings, docs, scripts,
tools/bin and the tools other than shaderc.

Local changes on top of that commit (keep them when re-vendoring):
- src/renderer_gl.cpp: the OpenGL renderer sets caps.vendorId to BGFX_PCI_ID_SOFTWARE_RASTERIZER when
  GL_RENDERER names a CPU implementation (llvmpipe, SwiftShader, GDI Generic...). Lime uses it to
  refuse software renderers; the vendor string alone does not tell them apart.
- src/bgfx.cpp: parseAttrTo reads its number with plain loops instead of bx::strFind, strCopy and
  fromString. Those measure a string up to INT32_MAX; inlined on a stack buffer, clang 23 could not
  link the 32-bit x86 Linux build with ThinLTO ("64-bit offset calculated but target is 32-bit").
- include/bgfx/bgfx.h, src/bgfx.cpp, src/bgfx_p.h, src/dxgi.cpp, src/renderer_gl.cpp, src/renderer_mtl.cpp,
  src/renderer_vk.cpp, src/renderer_webgpu.cpp: bgfx::getDeviceName returns the name of the device the
  renderer runs on (the DXGI adapter description, the Vulkan device name, GL_RENDERER, the Metal
  device name or the WebGPU adapter's device). It is empty for Noop and the console renderers. bgfx
  itself only exposes the PCI ids.
- src/bgfx.cpp: caps.limits.maxTextureSize is raised to 16384 when the renderer reports less. A
  renderer that reports 16384 or more keeps its own value.
- src/renderer_d3d11.cpp: Direct3D 11 no longer reports BGFX_CAPS_TEXTURE_DIRECT_ACCESS on Intel GPUs,
  so textures are not created through Intel's direct access extension. That path maps its staging
  copy without checking it was created, and crashed in ID3D11DeviceContext::Map at startup when the
  driver refused it. Nothing in Lime or OpenFL uses bgfx::getDirectAccessPtr.
- src/renderer_gles.h, src/renderer_gles.cpp, src/glcontext_gles.cpp (added), src/bgfx.cpp: on Windows and
  Linux the GL renderer is built a second time as OpenGL ES 3.0, in namespace bgfx::gles, and bgfx.cpp
  creates the OpenGL ES renderer from it. bgfx builds renderer_gl.cpp as either OpenGL or OpenGL ES, so
  desktop otherwise has no OpenGL ES. Windows creates the context with WGL (WGL_EXT_create_context_es_profile
  on the vendor driver), Linux with EGL.
- bgfx-files.xml builds bgfx with BGFX_CONFIG_VIDEO=0, so src/video_*.cpp only build their stubs. Lime has
  no binding for bgfx's hardware video decoding.
- src/dxgi.cpp: asking for BGFX_PCI_ID_SOFTWARE_RASTERIZER picks the Microsoft Basic Render Driver adapter
  (WARP). No adapter has that vendor id, so bgfx fell back to the first adapter, the GPU, and dropped WARP.
- src/renderer_gl.cpp: ShaderGL::create patches the shader source in heap memory, not on the stack. The
  source can be over a megabyte (SPIR-V Cross output after shaderc inlines everything), which overflowed
  the render thread's 1 MB stack on Windows.
